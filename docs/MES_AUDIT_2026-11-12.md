# Power2Go battery manufacturing system audit

Date: 12 November 2026. Reviewed version: package.json 2.1.7.

## Overall assessment

The application covers the operational chain from supplier receipts to cells, standalone modules, packs, flexible racks/cabinets, warehouse stock, issuance, sales, and traceability. It has a substantial normalized database design and several useful transactional RPCs. However, the checked-in implementation does not yet provide dependable enforcement of manufacturing quality or separation of duties. The most urgent work is authorization, trustworthy test evidence, release controls, and inventory state transitions.

This is a repository audit with local verification, not a certification of the deployed factory system. SQL findings describe the checked-in schema and migrations; the deployed policies, grants, function definitions, and migration history were not inspected. No live records were created, edited, deleted, or reset. The existing August report was treated as historical context, not evidence that its findings remain current.

## Coverage and verification

Reviewed the application shell, authentication and role loading, navigation, supplier/import entry points, production planning, cell/module/pack workflows, rack/cabinet assembly, inventory APIs, quarantine/rework/scrap, warehouse receipt/location changes, issuance/returns, sales, traceability entry points, audit/genealogy schema, machine gateway, consolidated SQL and relevant migrations, deployment scripts, and existing test coverage. Review followed the shared API/database paths; this was not a manual browser walkthrough of every control.

Local checks:

- `npm run lint`: passed (TypeScript compilation check).
- `npm run test:architecture`: passed; checks 20 required SQL object names and absence of active `mes_memory` references. It does not execute or validate SQL behavior.
- `npm run build`: passed. Vite warned about a chunk above 500 kB; the cell report export chunk is approximately 963 kB before gzip.
- Existing local tests run with `tsx --test` across `src` and `server`: 32 passed, 0 failed.
- `test:live` was inspected but not run: it writes to the configured live Supabase database and uses an administrator account. No isolated test database was established for this audit.

## Confirmed findings

### 1. Critical — The standard operator role receives full database authority

Evidence: `supabase/power2go_mes.sql:2948`, `:86`, `:2772`, `:3969`; `server/db.ts` seedConfigurationOnly; `server/routes.ts:364`.

The schema explicitly grants `ALL` to `role-operator`. The permission helper treats `ALL` as satisfying every permission, including user administration. Consequently, hiding Security or requiring an administrator on Express user-management routes does not prevent an operator from using the database policies directly. The operational reset RPC requires `MANAGE_USERS`, which `ALL` also satisfies. The legacy server independently seeds operators with `ALL`.

Impact: an ordinary production account can have authority to change security data and invoke a reset that truncates operational records, including audit history. This also prevents meaningful separation between an operator and a final quality approver.

Recommended change: replace `ALL` with explicit operational grants, enforce administration and final approval independently at the database boundary, and restrict reset to a separate maintenance mechanism. Check existing deployed grants after fixing seed definitions.

### 2. Critical — Cell-test RPC has no authentication or permission guard

Evidence: `supabase/power2go_mes.sql:1767` (`record_cell_tests_bulk`).

This SECURITY DEFINER function updates cells and battery progress and inserts test records without calling `require_permission`, checking `auth.uid()`, or validating that each cell belongs to the specified battery. The checked-in SQL does not revoke PUBLIC execution for this function. Actual anonymous exposure depends on deployed/default function grants and API configuration, which were not verified.

Impact: the function can bypass table RLS under its owner's privileges. Even an authenticated read-only caller must be rejected explicitly; supplied cell IDs and battery ID currently need not correspond.

Recommended change: explicitly revoke PUBLIC/anon execution, grant only the intended caller role, require the appropriate permission, and validate membership and eligible states before any mutation.

### 3. High — An empty or incomplete final test is recorded as passing

Evidence: `supabase/power2go_mes.sql:1985`; `src/services/api.ts:4117`; `src/components/production/BatteryPackWorkflowView.tsx:180`.

`record_battery_test_transaction` passes unless `qcTesting` is exactly `FAILED`; missing values default to pass. It does not enforce required measurements, numerical ranges, product limits, or prerequisite assembly steps. The pack UI defaults the outcome to PASSED and converts an empty/invalid IR input to zero.

Impact: a nominal EOL pass can be created without demonstrated electrical testing.

Recommended change: define versioned product test requirements; reject missing, invalid, and out-of-range measurements; derive the result from validated evidence. Keep imported evidence and manual attestations distinguishable.

### 4. High — Final release accepts historical passes and omits essential gates

Evidence: `supabase/power2go_mes.sql:2073`; `src/services/api.ts:4180` onward.

The release RPC checks that modules exist, that each has a QC pass now or at any time, that a controller ID exists, and that any historical EOL pass exists. It does not check the latest failed test, exact product/module/cell quantities, cell quality, controller test outcome, open quarantine on the assembly or its components, or whether evidence predates a component replacement. Some checks exist in browser `finalQc`, but direct RPC calls bypass those checks. The RPC uses general `MANAGE_PRODUCTION`, not a distinct final-approval permission.

Example: record an EOL pass, then a failure, then invoke release directly; the historical pass still satisfies the SQL condition. A module with an older pass and newer failure can also satisfy the historical module-test branch.

Recommended change: make the database release RPC the authoritative checklist, validate the latest applicable results against the current assembly revision, block all open holds, and require final-release authority.

### 5. High — Upload paths manufacture passing quality evidence

Evidence: `supabase/power2go_mes.sql:831`; `src/services/api.ts:1899`, approximately `:2139` and `:2251`.

Standalone module creation immediately creates a PASSED module, passing welding/QC records, and passing cell OCV/IR records with zero readings and grade A+. The module insert supplies QC JSON into the welding column and welding JSON into the QC column. Bulk battery upload similarly generates passing module tests and EOL records and completes the order without using the normal release checklist.

Impact: an imported assembly can look tested and released even when the upload contains component mappings rather than actual inspection evidence. Test history no longer reliably means a physical test occurred.

Recommended change: import assemblies as unverified unless source test evidence is supplied and validated. If historical finished-stock onboarding is intentional, give it a separate authorized acceptance workflow, provenance, original test dates, and explicit imported status.

### 6. High — Warehouse receipt and location changes can bypass lifecycle controls

Evidence: `supabase/power2go_mes.sql:2378`; `src/services/api.ts:5355`.

The general warehouse receipt RPC sets a battery to WAREHOUSE/IN_STOCK without validating its prior state, release record, quarantine, or rack membership. It also resets racks to IN_STOCK. The location-update API directly performs similar changes across separate requests.

Impact: receiving or moving an unfinished, quarantined, sold, or rack-contained entity can make it appear available again. Dispatch and rack assembly accept WAREHOUSE batteries, so this also creates a route around release checks.

Recommended change: separate initial receipt, warehouse transfer, and customer return; enforce allowed source states and ownership of nested components transactionally.

### 7. High — Direct table updates bypass the manufacturing state machine

Evidence: `src/services/api.ts:2831`, `:3024`, `:3928`; `supabase/power2go_mes.sql:2789`–`:2815`.

Authorized production users can update battery/module statuses and test records directly under broad table policies. `executeStep` marks any supplied step PASSED in AUTO mode by writing JSON, without machine execution or prerequisite validation. It overwrites a previously read step-results object, so concurrent changes can also be lost.

Impact: having transactional release functions does not enforce their invariants when equivalent state can be changed through another path.

Recommended change: restrict manufacturing mutations to validated commands/RPCs and keep administrative corrections separate, justified, and audited.

### 8. High — Bulk battery creation remains a multi-request operation with unreliable rollback

Evidence: `src/services/api.ts:1899`–`:2321`.

Bulk creation inserts orders, batteries, modules, cell assignments, test records, reservations, controller assignments, and completion status using separate requests. Compensating rollback does not inspect returned Supabase errors and resets cell state to FLOOR_STOCK rather than restoring each original state. A closed tab or lost connection can interrupt the sequence before cleanup runs. Browser serial-number allocation is also independent of database advisory locks used elsewhere.

Impact: partial imports, conflicting identifiers, inconsistent allocations, and incomplete cleanup remain possible even though normal order creation now uses a transaction.

Recommended change: use a server/database import command with atomic batches or a durable staged job, stable idempotency keys, and explicit reconciliation.

### 9. High — Issuance/return endpoints use service privileges without operation permission checks

Evidence: `server/routes.ts:892`, `:941`; `src/services/api.ts:5774`, `:5848`.

These endpoints require a session through shared middleware but have no `requirePermission` or active-profile check of their own. They write through the service client, bypassing RLS. Audit actor labels are supplied by the caller. The browser tries a direct database update after any non-success server response, including permission failures.

Impact: a read-only authenticated account can reach privileged issuance mutations; inventory changes may succeed even if audit insertion fails. Denied operations can take a different path instead of surfacing the denial.

Recommended change: require an operation-specific permission and active profile, derive identity from the verified session, commit the movement and audit together, and propagate authorization failures.

### 10. High — Quarantine rework is treated as successful release for modules

Evidence: `supabase/power2go_mes.sql:2162`.

`REWORK` and `RELEASE_APPROVED` share the non-scrap branch: modules become PASSED, cells return to available/reserved states, and controllers return to available/assigned states. There is no check preventing a resolved record from being resolved again. Quarantining/scrapping a child does not automatically hold its containing pack or rack.

Impact: work designated for repair can become eligible for assembly before repair and retesting. A finished parent may retain its released state while containing a defective child.

Recommended change: model rework as a blocked state with required repair/retest tasks; propagate parent holds and prohibit conflicting or repeated dispositions.

### 11. High — Production-order completion counters can lose concurrent increments

Evidence: `supabase/power2go_mes.sql:2138`–`:2149`.

Release locks the battery, then reads the order quantity without locking the order and later writes a computed absolute value. Concurrent releases of different batteries in the same order can read the same completed count and overwrite each other's increments.

Impact: released packs and production-order completion totals can disagree.

Recommended change: lock the order before reading it or perform an atomic increment with completion calculation using the resulting value. Test simultaneous releases of two packs in one order.

### 12. High — Schema deployment can discard custom roles and omit required migrations

Evidence: `supabase/power2go_mes.sql:2907` onward; `scripts/deploy-schema.mjs:28`; `supabase/migrations/20261110_dynamic_racks_and_cabinets.sql`; `supabase/add_inventory_manager_role.sql`.

The consolidated SQL rewrites custom-profile roles to operator and deletes roles/grants outside admin/operator/CEO. That conflicts with the separate inventory-manager role and custom roles exposed by the application. The deploy script executes the consolidated file, but does not apply the migrations directory. The frontend calls the four-parameter rack assembly RPC and queries shell-template data introduced only in later migrations; the consolidated file defines the older three-parameter RPC.

Impact: a rebuild can remove configured access boundaries or produce a database incompatible with current rack/cabinet screens. Re-running the old rack-serial migration after dynamic cabinets exist can also rewrite cabinet/fractional-capacity serials because its accepted pattern only recognizes integer-capacity P2G-RACK identifiers.

Recommended change: use an ordered migration history with recorded versions; keep seeds non-destructive and verify a clean install plus an upgrade from the prior version.

### 13. Medium — Standalone module completion does not prove every distinct cell was tested

Evidence: `supabase/power2go_mes.sql:950`–`:1036`.

Completion checks the submitted array length against the number of module cells and checks that each submitted ID belongs to the module, but does not enforce uniqueness or equality of the two ID sets. Repeating one valid cell can satisfy the length check. Numerical values must be present, but are not checked against limits; supplied grade text is accepted.

Recommended change: require exact distinct membership and product-specific measurement/grade validation, then derive module readiness from the stored results.

### 14. Medium — Module workflow writes accept unrelated modules and default missing checks to pass

Evidence: `supabase/power2go_mes.sql:1857`–`:1933`.

The RPC updates each supplied module ID without proving it belongs to `p_battery_id`. Missing visual or voltage checks default true, welding records contain fixed numerical parameters, and arbitrary permitted module statuses can be supplied without transition validation.

Recommended change: validate ownership, required check completeness, allowed transitions, and actual measurement provenance before writing.

### 15. Medium — Deletion performs side effects before its transaction

Evidence: `src/services/api.ts:3030`–`:3068`.

`deleteBattery` clears BMU/BMS reservations and battery links using separate writes before calling the cascade-delete RPC, which already owns deletion. If a later request fails, the retained battery has lost its controller relationships. Released/sold genealogy also requires a deliberate retention policy rather than routine destructive edits.

Recommended change: put all deletion prerequisites and relationship changes inside one transaction; use archive/void for production history where practical.

### 16. Medium — Audit records are append-only but their origin is not consistently trusted

Evidence: `supabase/power2go_mes.sql:582`, `:2837`; `server/routes.ts:926`; `src/services/api.ts:5830` onward.

Update/delete protection is a positive control. However, the audit INSERT policy permits readers to insert rows with arbitrary actor/action/entity values. Several client/server mutations write the audit separately and do not fail the operation when audit insertion fails. The reset RPC can truncate the log; row-level delete triggers do not protect against truncate.

Recommended change: generate audit entries at the authoritative mutation boundary using the verified identity. Distinguish maintenance resets from normal administration and preserve an external record of them.

### 17. Medium — Machines are simulated; rack quality attestations are not stored by assembly

Evidence: `server/machineAdapters.ts:15`; `src/services/api.ts:4095`; `src/components/production/RackAssemblyView.tsx` handle assembly; `supabase/migrations/20261111_fix_assemble_rack_for_update.sql`.

The machine gateway generates random/fixed readings. `testBms` supplies PASSED without receiving a measured test result. The rack UI asks for physical and voltage QC confirmations, but the assembly API/RPC does not receive or persist those confirmations. Rack compatibility is inferred mainly from pack capacity/template, rather than a validated electrical configuration and recorded rack test.

Recommended change: label simulation explicitly, add equipment adapters and measurement provenance where required, and store rack inspection/test evidence with its assembly revision. Treat the electrical acceptance rules as requirements to define with the manufacturing team.

### 18. Medium — Passing local tests do not establish factory workflow correctness

Evidence: `scripts/architecture-check.mjs`; existing `*.test.ts`; `.github/workflows/version-bump.yml`.

The 32 passing tests mostly verify parsers, mapping, status presentation, caches, ordering, and bulk-plan helpers. No isolated database test suite was found covering release bypasses, read-only permissions, concurrent allocations/releases, quarantine propagation, or interrupted imports. The inspected GitHub workflow bumps versions; it does not gate changes on these checks.

Recommended change: add isolated database integration tests and CI for the critical invariants before expanding workflows. Keep production-data tests distinct from automated validation.

## Improvements since the older audit

- Frontend permissions are loaded from role permissions; the old claim that every non-admin permission returns false is obsolete.
- Normal production-order creation now uses `create_production_order_transaction`.
- Cell, module, and controller assignment use transactional RPCs, with several row/advisory locks and uniqueness constraints.
- BMU assignment updates the battery's BMU link.
- Quarantine now supports both BMS and BMU in the database RPC.
- Audit rows have update/delete protection, and genealogy records support racks.
- Dynamic rack/cabinet shell support exists in the later migrations. It should not be assessed using only the legacy fixed-size rack function.

## Recommended order before adding features

1. Remove operator superuser authority, protect the cell-test RPC, and close service-client authorization gaps. Confirm the effective deployed grants in an authorized read-only database review.
2. Define one authoritative set of test/release rules. Make absent evidence fail closed and separate imported finished-stock acceptance from new manufacturing.
3. Enforce release, rework, quarantine propagation, warehouse transitions, and assembly revisions at the database boundary.
4. Make bulk creation and relationship changes atomic/idempotent; fix concurrent order counters.
5. Establish ordered migrations and isolated integration tests, then verify deployment and recovery on a non-production environment.
6. Add the requested features against those explicit workflows. Candidate extension points already exist for product templates, test specifications, module/pack/rack commands, stock movements, and genealogy events.
